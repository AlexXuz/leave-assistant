# Day17 · 异步执行与事件流：分级提示

任务见[异步 Agent 执行层](../tasks/async_agent_runtime.md)。先设计状态和观察证据，下面仅给排查方向，不提供完整执行器。

## 提示一：把等待画到同一时间轴

标出入队、获得槽位、发起调用、重试、结束。总期限从入场开始，单次调用期限不能超过剩余总时长。若只在获取信号量后开始计时，排队者会逃出预算。先用单调时钟和可控屏障测试，避免靠机器快慢得出结论。

只有独立调用才并发。工具B的参数依赖A结果时，必须等待A；模型一次提出多个工具也不意味着它们业务上可以并发。初版只接受宿主批准的只读工具，并拒绝重复tool_call_id。

## 提示二：明确哪些异常属于结果

查无记录、上游暂时不可用可以是工具协议结果；程序错误不应伪装成空数据。TaskGroup有任务抛出未处理异常时会取消同组其他任务。若要求收集各工具的可预期失败，应在每个工具包装层转换它们，并继续传播取消。

`asyncio.to_thread`可避免某些同步I/O阻塞事件循环，但取消等待不会强制终止运行线程；不要通过加一个线程就承诺“全部取消”。真实客户端需要传输层超时，写动作需要查权威状态和幂等策略。

## 提示三：让取消和重连各走自己的路径

订阅断开只清理订阅资源，显式取消才停止工作；两个入口不要共用一个未经区分的finally。取消发生在排队中、调用中和业务完成后，结果不同。用Event确认执行位置再取消，检查工具是否实际启动，不能只看界面文字。

SSE订阅负责读取持久事件，不执行工具。先校验任务归属，再按游标读取。生产者追加最后事件与更新终态时要有一致语义；消费者读完一次空列表后不能立即因终态结束而漏掉刚提交的最后一条。可让任务状态记录最后事件序号，并在退出前读取到该序号。

## 复核时需要解释

- 并发峰值是怎样测出的？总期限包含哪些等待？
- 谁持有并取消任务，连接/流由谁关闭，什么情况只能返回结果未知？
- 模型文本增量、工具事件与报告展示间隔有什么不同？
- 断线重连为什么不会重执行业务，最后一条终态如何保证能读到？
- 进程死亡后哪些状态还在，哪些工作不能恢复？

至少保留一次本机HTTP工具调用和一次真实异步模型调用，不能将全部内存替身测试称为外部链路验证。本人完成规则见[EVIDENCE_PROTOCOL](../EVIDENCE_PROTOCOL.md)。
