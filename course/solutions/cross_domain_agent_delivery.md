# Day24 · 分级提示：迁移与恢复

本页不提供完整应用。先提交新领域需求与状态设计，再选择需要的提示；旧 OA 规则变化不能替代跨领域项目。

## 提示一：先写成功条件

研发调查的输出可以是“与本次版本和时间窗口一致的证据、候选原因与下一步验证”，不要未经验证就承诺根因。研究项目要区分来源事实、推断、冲突和没有找到的证据。先写正常、缺信息、证据冲突与无法完成的判定，再设计工具。

列出至少两项不能从客服项目直接照搬的规则。例如时间窗口、日志脱敏、发布版本、来源时间和引用可信度。只把 order_id 换成 incident_id 不足以证明迁移。

## 提示二：分清状态和事实

把“Agent运行到哪里”“用户批准了什么版本”和“外部业务实际发生了什么”分别画出来。它们可能保存在不同系统，恢复时不必同时一致。

| 故障窗口 | 需要查证的事实 |
|---|---|
| 外部调用前退出 | 是否有持久化任务，是否仍有权限执行 |
| 外部已执行但响应丢失 | 远端能否按稳定动作 ID 读回或幂等重放 |
| 观察未保存时退出 | 已发生业务结果能否重新关联到原任务 |
| 人工等待中资料变化 | 原批准版本是否仍然适用 |

检查点里写了“将调用”不能证明已经调用，也不能证明没有调用。若外部接口不能幂等或查询，保留不确定状态并转人工，不能补一个新 key 假装重试成功。

## 提示三：恢复要换进程验证

使用独立测试 worker，故障开关只对专用任务生效。退出后启动一个新 worker，加载同一个持久任务 ID。记录恢复前后的检查点、外部动作记录和最终状态。不要让自己的内存对象在“模拟重启”后仍然存活。

两个 worker 抢同一个任务时，明确如何获得执行权、失去租约后怎么办、旧 worker 是否还能写入。数据库幂等约束仍需保留；不能只靠 Python 进程内锁。

## 提示四：把模型不确定性与恢复机制分开验证

先用确定性模拟响应复现故障窗口和副作用唯一性，再用真实模型执行新领域任务。前者不能当作效果指标，后者也不能替代故障窗口覆盖。Agent 轨迹可不同，但关键权限、版本与最终业务事实必须一致。

取消后观察后台工具是否仍在运行；已发送的外部写操作需要读回，不能仅看 UI 显示“取消”。恢复报告同时写清楚哪些取消是尽力而为、哪些动作有确定结果。
