# Day16 · Python 服务交付：分级提示与复核

先完成自己的设计与一次尝试，再逐层阅读。此文件不提供完整接线，不是成功报告；任务见[独立交付要求](../tasks/python_service_delivery.md)。

## 提示一：先写资源所有权

画出“谁创建、谁使用、谁关闭”。配置在启动时解析；HTTP客户端和数据库资源由应用 lifespan 管理；请求身份属于一次请求；业务处理端口由宿主注入。检查每条边是否把模型输出当成了可信状态。

将模块导入与应用启动分开验证。导入应不要求真实密钥/数据库；创建应用只注册路由和生命周期。真实资源直到启动时才打开，离线测试可替换资源工厂。

## 提示二：用失败顺序检查生命周期

不要只检查正常关闭。设第一个资源已打开、第二个初始化报错：第一个是否仍释放？可先用计数替身验证，再观察实际连接。异步上下文管理器与 AsyncExitStack 可管理多个资源，但错误仍要向启动层报告。没有资源就绪时不得返回可服务状态。

Python dataclass/TypedDict/Protocol 描述结构，Pydantic负责选定的运行时边界校验；两者不要混为一谈。给配置写清允许范围，不能接受零期限或负数并发。对字段校验失败返回客户端错误，外部模型不可用返回可辨认的依赖错误。

## 提示三：逐层排查容器

先确定失败在镜像构建、进程启动、依赖连接还是业务调用。容器内127.0.0.1是容器自身；镜像中缺失本机权重时，相关功能应明确不可用。比较镜像内实际入口与自己的源码，避免只验证了作者课堂应用。

健康检查不调用付费模型；真实模型可用性另跑一条请求并记录使用量。不要把环境中存在 Key 当成网络成功，也不要为诊断打印 Key。

## 复核时需要解释

1. 从干净环境执行哪些命令，哪个模块构建应用，哪些依赖在启动时创建？
2. 请求身份如何进入适配器，为什么不能从请求body或模型文本取？
3. 部分启动失败、正常退出和依赖失效各关闭了哪些资源？
4. 镜像、存活、就绪、真实模型调用和重启持久化分别有哪些证据？

参考课堂镜像可帮助理解部署结构，但不是本人的Python服务答案。本人提交及复核使用[证据规则](../EVIDENCE_PROTOCOL.md)。
