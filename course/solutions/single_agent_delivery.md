# Day19 · 分级提示：观察驱动的单 Agent

本页给设计和排查方向，不提供完整循环答案。先在自己的设计记录里写出目标、状态、工具和停止条件，再按需要查看下一层；如实记录所用提示。

## 提示一：先用一条任务检验数据流

选“用户给了订单号，但没有物流事实”的任务。在纸上画出：模型看见什么、提出什么调用、宿主执行什么、结果如何回到下一次模型请求。若所有调用都在模型第一次响应前固定执行完了，你做的是固定编排；它可以作为对照，但不是本课要验证的观察驱动循环。

核心入口是 `run_case(case, tools, *, model)`，评测入口是 `evaluate_case(case, tools)`。后者由你绑定实际模型适配器，不能因为命令传了 live 就自动认为调用了模型。先让一条正常任务跑通，再扩到追问、冲突和失败。

## 提示二：区分三个契约

- 模型适配器负责 messages、tool_calls、调用 ID、完成原因与供应商 usage 的转换。
- 工具接口负责 Schema、参数校验、宿主身份、业务状态与证据 ID。
- Agent 核心负责状态、观察之后的下一步、预算、错误恢复和终态。

先写一个明确标识的模拟模型适配器验证协议。再接真实模型，保留真实用量和调用记录。模拟协议正确不证明模型会选对工具。

课程工具通过 `tools.schemas` 发现，`await tools.call(name, arguments)` 执行；错误形状是 `{"status":"error","error":{"code":"INVALID_ARGUMENTS","retryable":false},"evidence_ids":[]}`。不要把工具失败直接丢出循环，也不要把所有错误都重试。未知工具、无权访问与临时依赖失败需要不同处理。

## 提示三：用四个问题检查每轮

1. 身份和允许工具是否仍由宿主控制？
2. 本轮结果能否匹配对应 assistant tool_call_id，消息裁剪是否保留整组？
3. 剩余步骤、工具次数与总时间是否允许继续，具体 I/O 是否拿到剩余超时？
4. 最终结论引用的证据是否本轮实际得到，未确认的内容是否保持未知？

不要要求模型输出隐藏思考过程来证明“会推理”。检查可观察的动作、工具结果、下一步选择和最终业务事实即可。同一任务可以有不同合理工具顺序，不应按唯一脚本轨迹判错。

## 提示四：从最小失败扩展

先令工具返回一次参数错误，观察模型是否修正；再令依赖短暂不可用，确认有限重试或部分结果；最后令模型反复请求同一工具，验证预算能终止。异步取消不自动保证远端停止，日志必须区分等待被取消与外部动作事实。

如果答案正确但评测失败，先检查 evidence_ids 是否真的从工具返回中取得；如果工具检查通过但语义不对，保留人工核验失败，不把回答改成 expected 关键词来“过题”。
