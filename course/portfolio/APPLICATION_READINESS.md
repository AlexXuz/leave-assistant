# 求职前的最小补强闭环

这不是要求补齐所有岗位要求后才投递。主项目通过独立验收、材料真实，并能解释下面三项后，可边投递边补岗位相关缺口。未执行事项明确写未执行。

## 1. 一次真实云环境小闭环

使用隔离教学数据与专用账号，按预算自主选择云资源；课件不会自动购买、部署或扩大公网权限。

- 从指定commit/镜像部署，域名/TLS与必要访问控制就绪；默认演示账号和公开demo密码不得直接用于公网开放。
- 密钥从云配置/受控环境注入，不进镜像、Git和前端；数据库不对公网开放。
- 浏览器实际完成登录、生成草稿、确认、提交、读回，保留脱敏申请编号与SQL状态。
- 重启应用后保留状态；发布一个小变更再回滚旧镜像；记录日志、依赖失败表现与恢复步骤。
- 说明备份/恢复、SSO、多实例哪些已做、哪些未做；不因一次云测试演示宣称生产HA或真实企业上线。

验收产物：云环境/日期/成本预算、commit与镜像摘要、访问控制说明、脱敏日志、演示和重启/回滚记录。资源用完按自己的计划停用，不为课程长期保留计费服务。

## 2. 提示注入与成本延迟的评估意识

按SECURITY_EVALUATION完成小型冻结评估集，明确模型输出与检索/工具文本都是不可信输入。真实权限和确认必须由后端强制。

至少报告：每个攻击输入、实际工具/SQL动作与业务结果；相同正常任务在基线/一次优化后的效果、失败、阶段耗时、端到端p50/p95、实际usage与缺失usage。成本按明确时间的供应商计费口径或标unknown，不把字符数乘固定价格冒充实际费用。

验收产物：逐案例结果与关键违规列表、预算触发记录、一次单变量对照及限制。小样本通过不代表系统安全或生产SLA。

## 3. 一个能讲清楚失败恢复的演示

推荐选“SQL已提交，模型说明失败”：展示请求编号、实际申请编号、预占状态；刷新后读回，再以同key重试说明；证明没有第二笔申请。也可选旧版本确认、模型不可达或任务worker失败，但须实际注入并保留观察。

五分钟内说明：用户看到什么→哪层失败→哪些事实可信→为什么这样恢复→如何验证没重复副作用→仍有什么限制。

## 投递决策

Day25聚焦一个主目标岗位族，关键要求有本人证据。遇到某岗位要求未完成的SSO/多实例/复杂文档能力，标注缺口与计划并选择合适岗位，不夸大。通过项目演示后开始收集面试反馈，不因选修无限延期。
