# Day11 · 业务工作流：预检、明确确认与幂等提交

## 交付目标与起点

草稿评估、确认与提交是不同动作。确认绑定本人、版本和内容；提交时读取服务端记录、复查余额并在同事务中预占和建单。模型解释失败不能抹掉已提交事实。

热身文件 `app/leave_submission.py`；独立任务文件 `course/projects/confirmed_application_workflow.py` 已创建。主线main从待实现骨架起步；作者示范有单独入口。alexstudy保留个人历史实现，不作为新学员默认进度。

## 输入输出与实现边界

prepare_application(text, services)只生成草稿；confirm_application(draft_id, revision, services)绑定用户看过版本；submit_application(draft_id, revision, key, services)复查状态和幂等，同key只返回原结果。支持范围外先说明，不硬套年假额度。

数据流：自然语言提取 → 后端预检/草稿版本 → 用户明确确认 → 提交复查/事务 → 一笔待审批申请 → 读回业务状态。

可在[独立工作区](../projects/README.md)接自己的页面/API，先用固定依赖替身理解，再按环境说明运行真实依赖。业务阶段不同，不能为了演示提前增加写权限或猜数据。

## 公开变体练习

1. 确认后修改日期/理由，旧确认必须失效。
2. 同一账号两笔申请竞争最后额度，不能都预检通过就都提交成功。

这些已经公开，不当作秘密留出题。冻结自己的基线，再领取变体；若已读或练过，请复核者换一条新的业务要求。

## 失败与恢复

SQL成功后模型说明超时，读回原申请并用同key恢复说明；事务中失败则无部分预占，不能把两类故障混成未提交。

算法/校验题通过修正数据并重新运行恢复，不强造进程崩溃。依赖错误和业务拒绝要保留具体观察。

## 验收标准

- **D11-C1**：确认绑定身份/版本/内容，确认不等于提交。
- **D11-C2**：提交原子、余额复查、幂等与并发拒绝有真实证据。
- **D11-C3**：已提交后失败仍保留业务事实，不重复建单或预占。

保存自己的正常、变体、失败与恢复记录；填写 `course/submissions/confirmed_application_workflow.json`。热身通过不等于整课完成，复核与哈希规则见[证据协议](../EVIDENCE_PROTOCOL.md)。CLI只用于辅助，主要交付应能从自己的页面、API或明确入口复现。
