# Day10 · Tool Calling：让模型查询真实业务事实

## 交付目标与起点

工具调用是模型提出结构化请求，后端验证并执行，再按tool_call_id回传。实时余额不在制度里；not_found不等于0。工具参数不能携带或覆盖用户身份。

热身文件 `app/office_tools.py`；独立任务文件 `course/projects/business_tool_pipeline.py` 已创建。主线main从待实现骨架起步；作者示范有单独入口。alexstudy保留个人历史实现，不作为新学员默认进度。

## 输入输出与实现边界

dispatch_tool(name, arguments, trusted_identity, services)只调用白名单只读业务；respond_with_tools(question, model, services)完整配对调用ID与结果，有界调用，不把工具返回文字当新授权。

数据流：用户问题 → 模型tool_calls → 参数/白名单/身份校验 → 业务或制度工具 → 对应ID的tool结果 → 有依据回答。

可在[独立工作区](../projects/README.md)接自己的页面/API，先用固定依赖替身理解，再按环境说明运行真实依赖。业务阶段不同，不能为了演示提前增加写权限或猜数据。

## 公开变体练习

1. 指定历史年份没有余额记录，保留not_found，不回答0。
2. 同时查询余额和审批制度，只有部分工具成功时明确缺口。

这些已经公开，不当作秘密留出题。冻结自己的基线，再领取变体；若已读或练过，请复核者换一条新的业务要求。

## 失败与恢复

业务接口超时、未知工具或额外身份参数拒绝，失败不能变余额0；恢复只读工具后有界重试，不产生写入。

算法/校验题通过修正数据并重新运行恢复，不强造进程崩溃。依赖错误和业务拒绝要保留具体观察。

## 验收标准

- **D10-C1**：身份来自服务端，模型只提业务参数。
- **D10-C2**：tool_call_id成对，白名单、Schema和错误传播正确。
- **D10-C3**：制度/余额/缺失记录分开解释，没有提交工具。

保存自己的正常、变体、失败与恢复记录；填写 `course/submissions/business_tool_pipeline.json`。热身通过不等于整课完成，复核与哈希规则见[证据协议](../EVIDENCE_PROTOCOL.md)。CLI只用于辅助，主要交付应能从自己的页面、API或明确入口复现。
