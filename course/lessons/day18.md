# Day18 · 用执行轨迹定位失败，核算效果、延迟与用量

目标：沿 Python 服务、模型、工具和业务状态定位故障，形成可复核的恢复与性能报告。先补轨迹，再注入故障，最后做同条件对照；不以安装某个监控产品作为完成条件。

## 一个请求与一个任务可能不是同一件事

request_id 关联一次 HTTP 请求，run_id/job_id 关联一次跨请求任务，step_id 关联模型或工具步骤，tool_call_id 对应模型请求的工具，业务编号关联最终事实。重连会产生新的 request_id，但不应该生成新的业务操作。服务端身份负责授权，这些追踪编号都不是授权凭据。

建议一条步骤事件包含：run_id、request_id、step_id、parent_step_id、phase、started_at、duration_ms、outcome、model/prompt_version/tool_version、脱敏参数概要、tool_call_id、error_code、attempt、usage 或 null。时间区分排队、模型首段响应、模型总时长、工具和端到端；并行步骤耗时相加不等于用户等待时间。

## 记录足够排障的信息，同时限制数据泄漏

参数采用允许字段列表，例如只记录订单编号的脱敏摘要、请求字段名和结果条数。不要默认打印所有 messages、检索文档、工具返回、Cookie或认证头。必要的语义复核材料放隔离产物，说明保留期限和访问范围；哈希只能帮助关联，不能让低熵个人信息自动匿名。

安全事件单独记录被拒绝动作、规则/策略版本和可信身份范围。检索文本说“自动退款”、工具返回要求追加权限时，记录实际请求与后端拒绝，而不是只统计最终答案是否出现危险词。

## 恢复依赖业务事实，不依赖模型措辞

已有请假案例中，SQL 已提交但模型说明超时；客服案例中，工单已创建但响应连接断开。两者都不能换一个幂等 key 再提交。恢复步骤是查权威状态：

| 查询到的事实 | 恢复动作 |
|---|---|
| 已成功，有业务编号 | 读回结果，必要时仅重试说明 |
| 明确未执行 | 在有效授权和预算内重试原动作 |
| 无法确认 | 标记未知，核对状态或人工处理，不能声称成功/撤销 |

轨迹重放分为“重算解释/评分”和“再次执行工具”。调试工具不得默认重新执行写操作；历史确认可能已经过期。模型重放也可能给出不同结果，须记录模型、Prompt、工具版本和新 run_id。

## usage 缺失并不等于零费用

例如两次模型调用分别返回 800 token 和缺失 usage，记录 `known_tokens=800`、`unknown_usage_calls=1`、`total_cost=null`；不能报告完整总量为 800 或费用为零。估算费用要单独标 estimated，并记录估算方法、价格来源及日期。实际费用以供应商口径核对，预算还须靠请求数、工具数与时间限制兜底。

比较基线与候选时使用相同场景、输入规模和并发，记录环境、模型、预热、样本数及失败。每个场景重复运行，区分网络不可用、任务失败、安全违规。报告端到端 p50/p95 和分阶段耗时，说明分位数算法和小样本限制；失败样本不能悄悄从报告消失。Day20再扩展到完整 Agent 任务完成率和轨迹评测。

## 一次完整的排障练习

先用依赖替身稳定复现“工具完成、模型解释失败”，再用本人服务和测试业务状态验证恢复。另用实际异步模型接口运行固定任务，收集真实 usage 与延迟。确定性替身证明故障处理，真实请求证明网络/模型链路，两个报告分别标注。现有 `scripts/benchmark_course.py` 只测本机只读 HTTP 接口，不可替代模型链路评估。

## 独立任务与完成条件

打开 [任务书](../tasks/failure_recovery_diagnostics.md)，沿用本人 `course/projects/failure_recovery_diagnostics.py`，增加自己的事件类型和采集适配器，保留已有函数。`classify_failure` 继续作热身，完整任务必须包含实际调用链与恢复证据。

本人记录仍是 `course/submissions/failure_recovery_diagnostics.json`。正常、公开变体、失败恢复各自留档；步骤、哈希和人工复核遵循 [证据规则](../EVIDENCE_PROTOCOL.md)。

## 生产还差什么，以及下一步

少量本机任务不能证明生产 SLA、容量或完整计费正确性。下一步在隔离部署中建立预算/超时告警，加入真实请求分布与持续回归；Day24验证恢复后轨迹连续，Day26交付可复现的部署故障演示。
