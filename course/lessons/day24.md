# Day24 · 把 Agent 迁移到新领域，并让任务可以恢复

目标：离开熟悉的客服和请假数据，从新需求设计工具、状态、成功条件与恢复机制。迁移不是替换字段名，也不是复制另一套完整作者答案。

**完成口径：** 交付一个非客服、非 OA 的 Python Agent 服务，接受新要求和真实进程故障，核对恢复后的外部业务事实。

## 选一个不同的问题

可以选择研发故障调查：从错误时间段出发，读取脱敏日志、服务依赖、近期发布与运行手册，产出带证据的候选原因和下一步排查计划。也可以选择资料研究：检索多份带版本的来源，发现证据冲突，补充检索并生成可追溯的调查报告。

从需求写出三张小表：有哪些可信事实和来源、允许哪些动作、怎样判定任务完成。故障调查的“找到根因”通常需要复验，不能因为模型给了听上去合理的解释就记成功；资料研究的“没有找到”也不是“事实不存在”。

原来的部门请假上限函数仍是普通规则变更热身，旧任务与个人代码保留。它不能替代本次跨领域验收。

## 哪些可以复用，哪些必须重新设计

复用模型适配器、消息协议、预算、追踪、工具执行框架和已验证的授权机制；重新设计领域工具、证据模型、任务结束条件、失败处理和评测案例。写出至少两个实质差异，例如日志时间窗口和时区影响证据、部署版本会改变运行手册的适用性。

不要提前安排一条永远执行所有工具的固定顺序。先用简单 workflow 建立可解释基线，再用需要观察才能选下一步的案例判断 Agent 是否值得增加成本。

## 检查点不是业务账本

Agent 状态可包含任务 ID、目标、消息组、证据引用、待人工动作、最近事件序号和运行状态。把状态保存在持久存储，服务端验证任务归属。恢复时重新读取关键业务事实；旧摘要不能证明一个动作已执行或仍被授权。

```text
工具准备 → 写入可恢复意图 → 调用外部服务 → 读回真实结果 → 记录观察
                               ↓ 进程可能在任意位置退出
恢复 → 查询幂等键对应的结果 → 复用已完成动作，或安全地继续
```

上图是需要设计的故障窗口，不是“先记一条状态就保证恰好一次”。如果远端没有幂等能力，也无法查询结果，返回结果不确定并交给人工处理，不能盲目重试。

## 人工决策也是有版本的输入

假设 Agent 建议创建一份测试工单或保存一份调查报告。界面应显示动作、目标、关键参数和版本；只有已认证用户的明确决定可以恢复执行。批准后任务资料变化，需要检查旧决定是否仍适用。

下面只是待恢复命令的示意结构，实际校验由你实现：

```python
command = {
    "task_id": "由宿主定位的任务",
    "expected_revision": 7,
    "decision": "approve",
    "action_id": "一次稳定的外部动作编号",
}
```

身份不放在模型参数里，`approve` 不由模型文本推断。共享检查点时，还要防两个 worker 同时恢复同一任务；可用租约/锁与版本检查，分别说明其保证和失效条件。

## 实际验证崩溃与重试

在自己的隔离 worker 进程中注入退出，不能停掉无关服务。至少覆盖“工具返回前退出”和“外部已写入、检查点未保存时退出”；重建 worker 后继续同一任务，读回外部状态，证明没有第二次副作用。只是在函数中 raise 后重新运行整个脚本，不等于验证进程重启恢复。

取消、暂停、失败与完成应可区分。用户取消后不再发起新工具；已发送的远端动作是否还能撤回，必须以工具契约和读回结果说明。对不可撤销的动作显示事实，不把取消 UI 当作回滚。

## 生产还差什么，以及下一步

一个隔离业务服务和少量 worker 并不等于生产高可用。先证明实际故障窗口、权限和幂等性，再按需求补租约续期、监控告警、容量与备份恢复；不为凑技术栈引入所有中间件。Day26 在独立部署环境复验整套交付。
