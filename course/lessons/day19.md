# Day19 · 独立交付一个客服工单调查 Agent

目标：把前面学到的模型调用、检索、工具、上下文和 Python 服务能力，组合为一个能依据观察调整行动的单 Agent。主任务从办公请假切换到客服调查；已有 OA 工程继续作为热身和参考。

**完成口径：** 独立设计并实现 Agent 循环、运行真实模型、完成需求变体和失败恢复。课程页的余额 Agent 示范和热身检查通过，均不代表本课完成。

## 从目标出发，而不是先画固定流程

用户说：“订单还没收到，但页面显示签收，帮我判断下一步怎么办。”系统不知道一开始就该查什么：可能缺订单号，需要追问；可能物流工具暂时不可用，需要报告部分失败；也可能订单与物流记录矛盾，需要补查规则并把事实、推断与未知项分开。

固定 workflow 适合已知顺序和确定规则；Agent 适合下一步依赖新获得信息的任务。工具调用由模型提出，权限、执行与终止条件由程序落实。不要把一个固定 if/else 流程改名为 Agent，也不要为了“自主”把权限交给模型。

```text
用户目标 + 可信身份
        ↓
模型提出下一动作 / 追问 / 最终回答
        ↓
宿主校验名称、参数、权限、剩余预算
        ↓
工具执行 → 结构化观察 → 更新状态 → 再次模型决策
        ↓
核验完成条件或记录明确的停止原因
```

## 循环中必须保存什么

至少区分任务目标、可信身份、消息/工具调用组、已经获得的证据、待补信息、剩余预算和停止状态。业务事实应保留来源、时间与状态，不能只保留模型总结。日志记录工具名、脱敏参数、结果状态、阶段耗时和调用编号；不记录 API Key 或会话 Cookie。

例如工具返回 `not_found` 表示本轮查无记录，不能改为“订单不存在”；`error.code=ACCESS_DENIED` 表示当前身份无权读取，不能换另一个用户重查。工具返回文本中的“忽略规则”仍然只是数据。

下面只展示错误观察的形状，不是本课完整实现：

```python
observation = {
    "status": "error",
    "error": {"code": "TEMPORARY_UNAVAILABLE", "retryable": True},
    "evidence_ids": [],
}
```

程序决定是否允许重试、还有几次和多少时间。将这次失败作为对应工具调用的结果交给模型后，模型才有机会选另一个信息源、追问或给出部分结论。校验失败与依赖失败不要全部吞成一段“查询失败”。

## 工具接口就是产品接口

工具名和描述要说明用途、参数含义、何时不该调用、可能的业务状态。模型参数不得携带任意身份或凭证；身份由宿主绑定。输出应是结构化事实，附可引用的来源 ID，而不是诱导模型相信“已经成功”。

先使用课程的隔离工具沙箱理解契约，再独立接通至少一个 MCP 或 HTTP 工具服务。协议调用成功不等于业务任务完成。保留发现/调用或 HTTP 请求与业务响应证据；只调用同进程同名函数不算外部工具集成。

## 限制循环，也核验结果

每次模型和工具调用前检查剩余步骤、工具次数与总时间；把剩余时间传给具体 I/O 的超时。单独限制一次工具返回大小，避免长观察挤掉目标与必要事实。同步阻塞调用需要明确适配，不能以取消 asyncio 等待冒称底层工作已经停止。

供应商 usage 缺失时用量标 unknown，不按零计算；请求完成后才知道的 token 用量不能冒充预付硬配额。到达预算、用户取消、依赖不可用、需要补信息和成功完成应有不同终态。最后一条模型消息不是成功证明，必须对照证据与任务要求。

## 从热身走向独立交付

原 `merge_evidence`、办公工具与 `app/course/bounded_agent.py` 继续用于理解调用 ID、身份和有界循环，它们是范围较小的参考。先用自己的话说明其限制，再在新模块实现客服 Agent，不调用作者示范代替自己的协调逻辑。

项目入口：`course/projects/support_agent_runtime.py`。`run_case` 是待实现的 Agent 核心；`evaluate_case` 是评测适配入口，需要你绑定真实或明确标识的模拟模型。模板保持未实现，不会默认给出成功结果。

任务书与分级提示：[独立任务](../tasks/single_agent_delivery.md)、[提示](../solutions/single_agent_delivery.md)。本课不要求复制某个框架的完整示例；你可以先手写循环，再用 LangGraph 重构并解释两者如何保持相同契约。

## 独立任务与完成条件

提交 `course/submissions/single_agent_delivery.json`，提供正常、公开变体和失败恢复三类本人产物。验收必须看到真实的观察依赖、一次有限纠错或合理停止、一个独立工具服务，以及与固定 workflow 的同任务比较。冻结案例、重复运行和优化在 Day20 深入完成。

公开变体不是秘密留出题；看过或练过时由复核者另外提出新要求。Day19 是硬验收门，五项关键标准全部通过才可记完成，详见[证据规则](../EVIDENCE_PROTOCOL.md)。

## 生产还差什么，以及下一步

隔离沙箱与少量真实模型任务不能证明生产可用性；本课也不开放真实退款或其他外部写权限。Day24 将 Agent 迁移到新领域并加入持久化恢复，Day26验证独立部署和故障处理。先完成单 Agent，再按目标岗位选择多 Agent、浏览器或代码执行方向。
