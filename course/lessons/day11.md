# Day11 · 业务工作流：预检、明确确认与幂等提交

目标：草稿评估、确认与提交是不同动作。确认绑定本人、版本和内容；提交时读取服务端记录、复查余额并在同事务中预占和建单。模型解释失败不能抹掉已提交事实。

## 先看完整数据流

```text
自然语言提取 → 后端预检/草稿版本 → 用户明确确认 → 提交复查/事务 → 一笔待审批申请 → 读回业务状态。
```

## 关键概念与责任边界

prepare_application(text, services)只生成草稿；confirm_application(draft_id, revision, services)绑定用户看过版本；submit_application(draft_id, revision, key, services)复查状态和幂等，同key只返回原结果。支持范围外先说明，不硬套年假额度。

代码职责分层：模型理解或生成建议；宿主注入身份/配置；确定性代码校验并执行；外部服务与数据库提供真实状态。当前单元只引入这一层需要的能力，不把后面的框架或生产系统提前堆进来。

Python中的dict/list是内存对象，JSON是文本；类型注解帮助IDE阅读结构，运行时约束需要Pydantic或明确检查。对已有Java经验，可以直接映射DTO、异常、事务与接口分层，但模型输出仍是不可信输入。

## 状态和故障：最小可核验案例

```text
草稿v1预检通过 → 确认v1：不建单、不预占。
提交v1/key1 → PENDING_APPROVAL：建一单、预占一次。
重试v1/key1：返回原单；修改为v2后拿v1确认提交：拒绝。
SQL已成功但说明失败：读回原状态，不再建单。
```

官方/原始资料：[参考](https://www.postgresql.org/docs/17/explicit-locking.html)。

4. 运行正常、变体、失败与恢复；逐条核对真实结果，再记录本人证据。

## 案例与失败定位

1. 确认后修改日期/理由，旧确认必须失效。
2. 同一账号两笔申请竞争最后额度，不能都预检通过就都提交成功。

失败场景：SQL成功后模型说明超时，读回原申请并用同key恢复说明；事务中失败则无部分预占，不能把两类故障混成未提交。

先定位发生在哪一层，再选修复动作。不能仅因网络失败换Prompt，不能以程序能跑就宣称语义正确，也不要求为了找模型错误刻意刁难。
