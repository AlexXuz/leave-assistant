# Day2 · Pydantic与评测：建立可执行的数据契约

目标：模型说是JSON，不代表字段正确。Pydantic负责类型/额外字段/日期，服务端负责日期关系、支持范围与missingFields。格式、业务和语义结果分开评估。

## 先看完整数据流

```text
助手字符串 → JSON解析 → Schema校验 → 日期/字段关系 → 服务端缺失字段 → 逐案例评测。
```

## 关键概念与责任边界

validate_extraction(payload, reference_time)返回严格校验的四字段与missingFields；map_validation_error(error)区分JSON、Schema、日期关系。自己定义DTO，避免把模型给出的missingFields直接当事实。

代码职责分层：模型理解或生成建议；宿主注入身份/配置；确定性代码校验并执行；外部服务与数据库提供真实状态。当前单元只引入这一层需要的能力，不把后面的框架或生产系统提前堆进来。

Python中的dict/list是内存对象，JSON是文本；类型注解帮助IDE阅读结构，运行时约束需要Pydantic或明确检查。对已有Java经验，可以直接映射DTO、异常、事务与接口分层，但模型输出仍是不可信输入。

## 服务端重算：最小可核验案例

```text
模型输出：{"leaveType":"ANNUAL","startDate":"2026-11-02","endDate":null,"reason":"家事","missingFields":[]}
服务端结果必须仍把endDate列为缺失。
字符串2026-02-30、结束早于开始、额外字段都是不同的校验条件。
```

官方/原始资料：[参考](https://docs.pydantic.dev/latest/concepts/validators/)。

## 案例与失败定位

1. 空白理由归一为空，非法日期与日期倒置分别拒绝。
2. 模型声称missingFields=[]，但结束日期缺失，服务端必须修正而不是放行。

失败场景：记录一个通过JSON语法但违反业务关系的输出，修正校验后重跑冻结案例；保留修正前结果，不只展示最终通过。

先定位发生在哪一层，再选修复动作。不能仅因网络失败换Prompt，不能以程序能跑就宣称语义正确，也不要求为了找模型错误刻意刁难。
