# Day26 · Python 大模型应用工程综合验收

目标：独立交付、评估和维护一个 Agent 应用，并证明能把公共能力迁移到新业务。原有 Java 等后端经验是学习起点；毕业成果使用 Python，不要求 Java 服务或 Java AI 框架。

**完成口径：** 以本人客服 Agent、跨领域 Agent、评测报告和实际部署为依据。能复述术语或依次点击作者 OA 演示，不计综合完成。

## 一场围绕产品结果的演示

从本人 Python 服务接收任务开始，展示宿主身份、模型如何依据工具观察调整下一步、证据如何进入回答、信息不足时如何追问、何时停止。接着查看一次完整追踪和可核验业务结果，说明使用 MCP、HTTP、Skill 或工作流的具体理由。

再切到 Day24 的新领域项目，说明哪些基础组件复用了、哪些契约必须重设计。评审提出一条真正没练过的需求，例如来源版本冲突或外部动作返回不确定；你先分析影响，再实现和运行验证。公开题目不能自动当作未见题。

RAG、文档、受控 SQL 与图表仍是课程基础能力，可用既有本人产物证明；本次毕业应用不必强行把每项技术塞进同一条用户流程。SFT/LoRA 的实验边界也必须解释清楚，随机微型模型实验不能写成业务大模型优化。

## 部署验收看什么

从明确的 commit/镜像在与日常开发进程分离的环境部署，可以使用已有隔离云主机。演示访问控制、配置/密钥注入、健康检查、任务状态持久化与日志检索。展示一个版本发布、一次回滚和一次 worker 重启恢复。仅打包成功或本机 GET 接口可用不算完整部署交付。

对公网环境落实认证/TLS与数据库隔离，教学默认账号不得直接开放。课件不会自动购买云资源。报告已验证环境、预算与限制；没有运行的生产能力如实列缺口。

## 效果、可靠性与成本一起看

使用 Day20 冻结的任务集，展示逐任务和多次重复结果。任务完成率、关键越权、无效循环、恢复失败、费用和延迟必须能追到原始记录。模拟模型用于协议和故障回归；真实模型报告必须记录模型版本、Prompt/工具版本、用量缺失与网络失败。

一张总体分数不能掩盖越权或重复副作用。固定 workflow 在相同任务与预算下更合适时，可以采用它；你需要解释取舍，而不是证明 Agent 永远更好。最终业务状态与引用来源比“回答看上去合理”更可信。

## 面试追问用自己的代码回答

1. 你的 Agent 哪一步由观察决定？如果换成固定 workflow，什么任务会变差，什么任务反而更合适？
2. 一个同步 SDK 放进 async 路由会影响什么？取消等待后，线程或远端工具是否真的停止？
3. 工具参数错误、业务查无记录、连接超时怎样反馈？哪些可以重试，哪些必须停下？
4. 工具消息压缩后怎样保留调用 ID 与关键事实？旧记忆与最新业务状态冲突怎么办？
5. 外部写入成功但检查点未保存时，恢复依据什么事实？为什么不会产生第二笔操作？
6. 模型回答很好但任务未完成，评测如何发现？usage 缺失时如何报告成本？
7. RAG 没命中、证据冲突与权限不足分别怎么处理？受控 SQL 为什么还需要数据库权限？
8. 哪些限制来自课程样本，哪些是实际部署尚未补齐的能力？下一步怎样验证？

先录下本人答案，再看[提示与讨论](../solutions/final_assessment.md)。每个回答应能定位到自己的代码、请求编号、报告或状态读回，允许承认未知。

## 独立故障与复核

在约定的隔离依赖中注入超时、错误响应、worker 退出或过期人工决策。先看事实再恢复，不清空共享数据库、不关闭无关进程、不用新幂等键掩盖旧操作。

综合自检可按独立复现、数据流解释、边界识别、故障处理、需求迁移和证据准确性分别打分，但关键越权、重复副作用、伪造成功和虚构证据不能被总分抵消。课程通过不是招聘录用或生产经验认证。
