# Day7 · 知识生命周期与权限：快照、事务和授权检索

目标：完整快照才能推断删除；规划和执行分离。元数据变化、正文变化与不变要区分，写库时复查来源版本，旧批次不能覆盖新批次。授权必须先于TopK和模型。

## 先看完整数据流

```text
同来源完整快照 → 同步计划 → 事务/版本复查 → 更新片段与清单 → 权限SQL过滤 → TopK → 授权消息。
```

## 关键概念与责任边界

synchronize_source(snapshot, store, embedder)规划后再事务应用，失败回滚；prepare_visible_request(question, trusted_access, store, top_k)从服务端身份派生来源/部门范围，过滤后再排名。

代码职责分层：模型理解或生成建议；宿主注入身份/配置；确定性代码校验并执行；外部服务与数据库提供真实状态。当前单元只引入这一层需要的能力，不把后面的框架或生产系统提前堆进来。

Python中的dict/list是内存对象，JSON是文本；类型注解帮助IDE阅读结构，运行时约束需要Pydantic或明确检查。对已有Java经验，可以直接映射DTO、异常、事务与接口分层，但模型输出仍是不可信输入。

## 变化分类：最小可核验案例

```text
同一来源：新ID→INSERT；正文/向量指纹变→REINDEX；只改标题/定位→METADATA_ONLY。
仅完整快照中消失的旧ID→DELETE；非完整快照禁止据此删除。
计划基于版本r1，执行时来源已变r2，必须冲突而不是覆盖。
```

官方/原始资料：[参考](https://www.postgresql.org/docs/17/tutorial-transactions.html)。

## 案例与失败定位

1. 只改标题/定位与改正文分别走不同更新策略。
2. 无部门权限时只见明确公开材料，不能用过滤后的TopK缺口作为放宽权限理由。

失败场景：事务中途失败后读不到半成品；旧批次遇到更新后的来源必须冲突。重新规划同快照可以成功，不重复编码不变正文。

先定位发生在哪一层，再选修复动作。不能仅因网络失败换Prompt，不能以程序能跑就宣称语义正确，也不要求为了找模型错误刻意刁难。
