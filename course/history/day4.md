不能把排序算法验收通过理解为模型语义排序一定正确。算法按分数排序可能完全正确，但 Embedding 给出的顺序仍会偏离回答所需证据。

Top-K 指最多选多少个候选，不保证候选都相关，也不保证证据齐全。分数不是正确概率。年假问题里 0.5477 的“申请时间”并不比 0.5390 的“年假审批”更能回答审批人问题。

缺少年假条款时，不应要求生成模型编出本公司的审批规则。先检查检索，再检查上下文，再检查生成，才能定位失败。

## 当前作业：准备 RAG 请求

实现 app/rag_qa.py 的 prepare_rag_request(question, top_k=2)。函数不调用聊天 API，负责把已经实现的组件串起来：

```text
load_chunks
  → embed_documents(片段正文列表)
  → embed_query(问题)
  → rank_chunks(问题向量, 片段向量, 原片段, top_k)
  → 命中片段转参考资料
  → build_policy_messages(问题, 参考资料)
```

只把实际命中片段交给模型，不读原始全文来补入其他内容。这样之后才看得出检索本身是否足够。

### 来源从文档细化到片段

rank_chunks 的每项为 {"chunk": 完整片段字典, "score": float}。
build_policy_messages 接受的每份资料为 {"id": "来源 ID", "content": "资料正文"}。

把命中结果适配成：

```python
{
    "id": "leave-policy:2026-10-15-v1:2",
    "content": "青禾实验室请假制度\n年假审批\n……完整条款……",
}
```

每个片段作为一份独立参考资料。继续复用现有消息函数和 PolicyAnswer；sources 现在填写实际提供的片段 ID，而非原来的整份文档 ID。document_id、heading、version 等原始元数据仍保存在 retrieved_chunks 中，便于追溯。

### 返回结构

```python
{
    "retrieved_chunks": rank_chunks返回的列表,
    "documents": 适配后的参考资料列表,
    "messages": build_policy_messages返回的消息列表,
}
```

普通循环就可以实现，不要求列表推导式。核心是保持片段顺序与内容对应，不重新实现向量计算、排序、Prompt 或 JSON 校验。
